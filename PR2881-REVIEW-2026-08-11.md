## 1. Verdict

The branch does what its title says, and it does it thoroughly: UK Open Banking consents move from "granted to the real PSU" to a per-consent shadow user, which is the model Berlin Group and OBP-native already used, and the Berlin Group authorisation pair stops minting challenges for whoever happened to hold the token. The reasoning is written down at every site, the account-holdership gate that Berlin Group never had is now applied at both the start and the answer of an authorisation, and revocation finally drops the `AccountAccess` rows instead of only flipping a status column. Automated checks are green and SonarCloud passes. This is good work.

**It should not be merged as it stands.** Two defects undercut the change on the exact path the standard specifies, and one of them makes the branch's own headline fix inert on any existing installation:

- **F1** — on the OAuth2 access-token path (the normal UK path), *every* failure inside the principal swap is swallowed and the request silently continues **as the PSU**, with the PSU's own account access and no constraint from the consent's Permissions. That includes the refusal commit #74 deliberately added, and it includes a failure to grant the consent's views. The Consent-Id header path refuses the same consent. `checkUKConsent` does not re-check either condition.
- **F2** — the system-view permission split (`ReadBalances` no longer implying full transaction visibility, `Detail` actually exceeding `Basic`) is applied only when a view row is **created**. On any database where those views already exist, nothing in this PR changes them, and no migration ships. The defect the commit names survives the upgrade.

F1 is the blocker. F2 is a blocker for the claim the commit makes, if not for the merge.

Everything else below is smaller: one API-compatibility question the project's own versioning rule answers (F4), two fail-open paths worth closing (F5, F6), and a set of comments that now describe code that no longer exists or has since been written (F7, F8).

The merge conflict was real but narrow, and is now resolved — see §2.

### F1 — A UK consent presented in an access token falls back to full PSU access when the shadow-user swap fails · **HIGH** · `CONFIRMED`

**Where:** [`ConsentUtil.scala:1074`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L1074), reached from [`APIUtil.scala:2986`](obp-api/src/main/scala/code/api/util/APIUtil.scala#L2986)

```scala
scala.util.Try(swap).toOption.flatten.getOrElse((user, callContext))
```

`swap` is an `Option` for-comprehension whose last step is `resolveUKConsentPrincipal(...).toOption`. Every way that can fail collapses to `None`, and `None` means **leave the request exactly as it was** — authenticated as the PSU.

The comment above it says the swap "performs no validation and cannot widen anything: it either narrows the principal to the consent's shadow user or leaves the request exactly as it was." That is true of the *swap*. It is not true of the *outcome*, because `resolveUKConsentPrincipal` is not only a resolver — since commit `3c8e952f9` (#74) it is also a **refusal**:

```scala
// ConsentUtil.scala:1133
Failure(ErrorMessages.ConsentNamesNoAccount)
```

On the Consent-Id / Consent-JWT header path that `Failure` propagates and the request is refused ([`ConsentUtil.scala:883`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L883), inside a `Box` for-comprehension). On the token path it becomes `None` and the request proceeds as the PSU — precisely the behaviour #74's commit message describes and rejects: *"the PSU's own AccountAccess rows govern, so the TPP saw everything the PSU can see and the consent's declared Permissions constrained none of it."*

Nothing downstream recovers it. `checkUKConsent` ([`ConsentUtil.scala:2172`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L2172)) checks standard, status, not-before, expiry, PSU binding and consumer — **not** whether the consent names an account, and not whether its views were granted. Its PSU comparison reads `consenter` *falling back to* `user` (line 2216), so with `consenter` unset it compares the consent's owner against the PSU and passes. The v4.0.1 and v3.1 read endpoints resolve accounts purely from the principal's `AccountAccess` rows (`Views.getPrivateBankAccountsFuture(u)`, `ViewNewStyle.checkViewsAccessAndReturnView`), so the principal *is* the scope.

**Failure scenario A — the one #74 was written for.** A UK consent authorised before account binding existed (JWT views are the `(null, null, permission)` placeholders `createUKConsentJWT` writes), status `AUTHORISED`, `uk_consent_allow_unbound_legacy` unset. The TPP calls `GET /open-banking/v4.0.1/aisp/accounts` with a Bearer token carrying the `consent_id` claim. → swap returns `None` → principal stays the PSU → `checkUKConsent` passes → **the TPP reads every account the PSU holds**, unconstrained by the consent's Permissions. Over the Consent-Id header the same consent gets `OBP-35040`.

**Failure scenario B — far more reachable, and it needs no legacy row.** `grantAccessToViews` returns `Failure(CouldNotAssignAccountAccess …)` when any view named by the JWT resolves to neither a system nor a custom view ([`ConsentUtil.scala:472-485`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L472)). `ReadTransactionsCredits` is **new in this PR** and, like every view in that family, is only created when the operator lists it in `additional_system_views` ([`Boot.scala:320-343`](obp-api/src/main/scala/bootstrap/liftweb/Boot.scala#L320) iterates the *props* value and filters it against the allow-list — the PR adds the constant to the allow-list and to `sample.props.template`, neither of which touches a deployed `props` file). Meanwhile `validateUKConsentPermissions` ([`ConsentUtil.scala:1552-1559`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L1552)) *requires* one of `ReadTransactionsCredits`/`ReadTransactionsDebits` whenever a transaction-depth permission is granted. So on any instance upgraded without editing props, a perfectly conforming consent for `["ReadAccountsBasic","ReadTransactionsBasic","ReadTransactionsCredits"]` → grant fails → swap returns `None` → **the TPP reads all of the PSU's accounts**. The failure mode is silent and the response is a normal `200`.

Worse in kind: the grant is partial. The shadow user has already received the views that *did* resolve, and the request is served as the PSU anyway.

**Test coverage.** `UKOpenBankingV401ConsentScopingTests.scala:240-268` exercises the token path twice — the happy path, and a token with no `consent_id` claim. Neither failure branch is covered. `ConsentNamesNoAccount` appears in zero test files.

**Why the local probe matrix did not catch it either.** `.local-testing/OBP-Hola/run_probes.py:157-177` already builds exactly the scenario-A consent — a real AUTHORISED consent whose JWT is rewritten to the placeholder shape and re-signed with the consent's own secret — and asserts it is refused with `OBP-35040`. It passes, and it always did. It drives the consent through `harness.consent_headers()`, which is the **Consent-Id header** path ("the consent alone, no Authorization"). The header path refuses correctly; the token path is the one that fails open. So #74's "drives it over HTTP: 105/105" is accurate and still leaves the path the UK standard actually specifies untested. Probe count is not coverage.

### Reproduced end to end, then fixed (2026-08-12)

Driven over the real Bearer-token path against a running instance built from `d7af623ec`, using a genuine OBP-OIDC access token for the PSU carrying the `consent_id` claim (OBP-OIDC's `/auth` accepts `consent_id` and passes it to `generateCodeForUser`, so the whole ceremony is a form POST plus a code exchange — no browser needed). Same consent, same request, two builds:

| build | consent bound to an account (control) | same consent, JWT rewritten to the placeholder shape |
|---|---|---|
| with the fix | `200` | **`403` + `OBP-35040`** |
| without the fix | `200` | **`200`, serving the account** |

**One correction to the claim above.** Both scenarios say "the TPP reads every account the PSU holds". What the unfixed build actually does is **serve the request instead of refusing it**; how much data that exposes depends on what the PSU holds *in their own right*. On the test instance the first unfixed run returned `200` with an **empty** account list, because that PSU holds only `owner`, `ManageCustomViews` and the three Berlin Group views — no `ReadAccountsBasic`/`Detail`, which is what the UK endpoint resolves against. Granting the PSU a single `ReadAccountsBasic` row and re-running produced `200` with the account fully serialised.

That is not a mitigation, because the grant is exactly what an upgraded instance has: **before this PR, UK consents granted their views to the real PSU**, so every consent a PSU had ever authorised left those rows behind on them. So the accurate statement is: on a *fresh* instance F1 is "refuses nothing that should have been refused"; on an instance *upgraded* from the pre-shadow-user behaviour it is a data leak whose extent is the union of every UK view the PSU accumulated — the same population F2 affects.

**Fixed** in [hongwei1/OBP-API#79](https://github.com/hongwei1/OBP-API/pull/79) (`97f43b03f`, `025ada120`), which targets `develop-obp` and so reaches this PR on merge.

**A second gap, found only by reviewing that fix.** The first commit put the refusal in `checkUKConsent`, which only the UK data-read endpoints call — so the same request was still served the PSU's full scope by every other endpoint family, and the failure path was *wider* than the success path there (a successful swap narrows the principal everywhere; the failed one did not). `ResourceDocMiddleware` now applies the refusal to every endpoint it wraps, exempting the `account-access-consents` family so a TPP can still inspect and revoke the consent in question. Verified the same way: without the middleware wiring `GET /obp/v5.1.0/my/accounts` returns `200` with the account, with it `403`, and the UK and exempt endpoints are unchanged in both.

Worth recording, because it is the same shape twice: **every check that was green before that review — unit, mutation, end-to-end — only ever drove UK endpoints.** The defect survived them for the same reason F1 survived the probe matrix. The coverage was not thin, it was aimed at the path we had in mind.

**Suggested direction.** The swap has to distinguish "this token has nothing to do with a UK consent" (leave alone) from "this token names a UK consent that cannot be resolved" (refuse). Once `storedConsent` is found and its `apiStandard` is `UKOpenBanking`, the request is committed to the consent, and a `Failure` from `resolveUKConsentPrincipal` should become the request's outcome rather than a fallback — the same value the header path already propagates. The `Try(...)` should stay only around the genuinely-optional lookups before that point.

### F2 — The system-view permission tightening never reaches an existing installation · **HIGH** · `CONFIRMED`

**Where:** [`MapperViews.scala:720-731`](obp-api/src/main/scala/code/views/MapperViews.scala#L720) (`getOrCreateSystemView`) vs [`MapperViews.scala:836`](obp-api/src/main/scala/code/views/MapperViews.scala#L836) (`applyDefaultsForSystemView`)

The PR replaces the shared `SYSTEM_VIEW_PERMISSION_COMMON` on seven UK views and adds permission sets to the two Berlin Group views that had none. `constant.scala` states the defect it closes: *"Previously all six shared SYSTEM_VIEW_PERMISSION_COMMON, so 'Detail' granted nothing beyond 'Basic' and Balances alone exposed full transaction data."*

`applyDefaultsForSystemView` has exactly two callers: `unsavedSystemView` (line 822 — **creation only**) and `factoryResetSystemView` (line 979). `getOrCreateSystemView` returns `Full(v)` untouched when the row exists. Boot calls `getOrCreateSystemView`.

**Failure scenario.** An operator upgrades an instance that has been serving UK Open Banking. `ReadBalances`, `ReadAccountsDetail`, `ReadTransactionsDetail` etc. already exist in `viewdefinition`, each with the generic permission set. Boot finds them and leaves them alone. A consent scoped to `ReadBalances` alone continues to expose full transaction and counterparty data; `ReadAccountsDetail` continues to grant nothing beyond `ReadAccountsBasic`. The upgrade appears successful and the vulnerability the commit names is untouched.

`git diff --stat bbe26e161..develop-obp -- obp-api/src/main/scala/code/api/util/migration` is empty — no migration ships. The only remedy in the codebase is a per-view admin call to `POST /obp/v7.0.0/management/system-views/VIEW_ID/factory-reset`, and nothing in the PR, the props template or `docs/operations/CONSENT_STALE_ACCESS.md` says an upgrade requires it.

**Test coverage is present but cannot catch this.** `MappedViewsTest.scala` asserts each view's `allowed_actions` matches its target set exactly — via `getOrCreateSystemView`, in a suite whose `afterEach` runs `ViewDefinition.bulkDelete_!!`. It therefore always tests the **creation** path, which is the path that works. The comment in the test says as much ("creates them fresh with current code defaults"). It is good coverage of the new constants and no coverage at all of the upgrade.

**Fixed** in [hongwei1/OBP-API#80](https://github.com/hongwei1/OBP-API/pull/80) (`ffc4d15e0`) — but **not** as a migration. `Migration.runOnce` is gated on `migration_scripts.execute_all`, which defaults to `false`, so a migration would have reproduced the very shape of this defect: a fix that does not apply to the installations that have the problem. Boot now calls `ensureSystemViewUpToDate`, which re-applies the code-defined permissions to existing rows, with an opt-out prop defaulting to true. Written test-first: the new upgrade scenario fails before the change with `ReadAccountsBasic` still carrying the 74-permission generic set. One gap left open there — the two Berlin Group views' real state on a long-lived database is not established; one development database has `ReadAccountsBerlinGroup` carrying 176 distinct permissions accumulated across three dates, which is neither the generic set nor the target, and upgrading from that shape is untested.

**Original suggested direction, for the record.** A migration that re-applies `applyDefaultsForSystemView` to the nine affected system views, guarded so it runs once. If a blanket re-apply is considered too blunt (it would also discard an operator's deliberate edits to those rows), then at minimum the props template and the operations doc must state that the reset endpoint has to be called per view on upgrade, and the release notes must say the fix is opt-in. Silently shipping a security fix that does not apply to the systems that have the problem is the worst of the three options.

### F3 — `getConsentInfo` and the account-consent GET/DELETE let a stranger through when both ids on the consent are blank · **LOW** · `PLAUSIBLE`

**Where:** [`ConsentUtil.scala:1719-1721`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L1719) (`psuOrLodgingTppRefusal`)

```scala
val owner = present(consentConsumerId)
if (owner.forall(id => callerConsumerId.flatMap(present).contains(id))) None
else Some(ErrorMessages.ConsentDoesNotMatchConsumer)
```

`Option.forall` on `None` is `true`. A consent with neither a bound PSU nor a lodging consumer id is therefore readable and revocable by any authenticated caller. The scaladoc treats blank as "absent" deliberately, for rows that predate consumer binding.

I could not construct a reachable state on current code: the lodging endpoints reject a request with neither user nor consumer, and every pre-existing row was written by code that always passed a user. So the grandfathering is probably inert — but it is the same shape as the legacy fallback #74 chose to *close* rather than keep, and the two decisions point opposite ways. Worth a deliberate answer rather than an inherited default.

### F4 — `authoriseUKConsent` adds a required body field to a released API version · **MEDIUM** · `CONFIRMED`

**Where:** [`Http4s510.scala`](obp-api/src/main/scala/code/api/v5_1_0/Http4s510.scala), `PostUKConsentAuthoriseJsonV510`

```scala
-case class PostUKConsentAuthoriseJsonV510(challenge_id: String, answer: String)
+case class PostUKConsentAuthoriseJsonV510(challenge_id: String, answer: String, account_ids: List[String])
```

plus a new guard rejecting an empty `account_ids` with 400.

The change itself is right — it is the whole point of the Gap 4 remediation, and a consent that binds to no account is the thing F1 is about. The problem is where it lands. `CLAUDE.md` states the project's own rule: *"API version numbers reflect API signature changes (new/changed fields, new behaviour)."* This is a new required field and new behaviour on **v5.1.0**, an already-published version. Any existing client posting `{challenge_id, answer}` now gets a 400 after upgrade.

**Suggested direction.** Either introduce the field in a new version and leave v5.1.0's shape alone, or — if v5.1.0's UK authorise endpoint is understood to be pre-release and has no callers — say so explicitly in the PR description, because the diff does not distinguish the two cases and a reviewer applying the project's rule will read it as a violation.

### F5 — `assertBerlinGroupConsentAccountsHeld` treats an unreadable consent JWT as "names no accounts" · **MEDIUM** · `PLAUSIBLE`

**Where:** [`ConsentUtil.scala:1804-1808`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L1804)

```scala
val consentAccounts: List[(String, String)] = JwtUtil.getSignedPayloadAsJson(storedConsent.jsonWebToken)
  .map(... .extract[ConsentJWT])
  .map(_.views.map(v => (v.bank_id, v.account_id)).distinct)
  .getOrElse(Nil)
```

`getOrElse(Nil)` merges two different states. The scaladoc justifies the empty case — *"A consent whose JWT names no account yet is not refused here. That is the availableAccounts ('allAccounts') shape"* — and that reasoning is sound for a JWT that genuinely lists nothing. It does not cover a JWT that could not be read.

**Failure scenario.** A consent row whose `mjsonwebtoken` no longer parses or no longer extracts into `ConsentJWT` (a schema change to `ConsentJWT`, a truncated write, an operator edit). `notHeld` is empty, `allHeld` is `true`, and the account-holdership gate — the control the scaladoc calls out as *"the security control that stops a consent being bound to somebody else's accounts"* — passes for a consent whose accounts are unknown. Both `startConsentAuthorisationAll` and `updateConsentsPsuDataAll` then proceed.

Note that the *same* expression shape is what the prior review (§4) identified as able to throw a `MappingException` in `revokeConsentAccountAccess`. It is the same fragility read from the other end: there it propagates, here it is swallowed.

**Suggested direction.** Distinguish `Empty`/`Failure` from `Full(Nil)` and refuse on the former.

### F6 — `findPsuByPsuId` accepts deleted and locked users · **MEDIUM** · `PLAUSIBLE`

**Where:** [`ConsentUtil.scala:1940-1946`](obp-api/src/main/scala/code/api/util/ConsentUtil.scala#L1940), backed by [`LiftUsers.scala:101-116`](obp-api/src/main/scala/code/users/LiftUsers.scala#L101)

Neither `getUserByProviderAndUsername` nor the new `getUsersByUsername` filters `IsDeleted`, and neither consults `LoginAttempt.userIsLocked`.

**Failure scenario.** A TPP sends `PSU-ID: <username of a deleted or locked PSU>` on `POST /berlin-group/v1.3/consents/{id}/authorisations`. `resolvePsuIdHeader` resolves it, `resolveBerlinGroupPsu` returns it, and `createChallengesC2` mints a challenge for that user — `createChallengeInternal` delivers the OTP to the addresses on the resolved user's record. A PSU whose account was deleted or locked still receives authentication traffic.

Whether the consent can then actually bind depends on `assertBerlinGroupConsentAccountsHeld`, so the exposure is the unsolicited OTP rather than access — but "we deliver authentication codes to deactivated accounts" is its own problem, and this is a **new** entry point for it introduced by the PR.

This is the same root as the deferred item `2026-08-10-obp-locked-psu-consent-still-live` (see §5), reached from the other direction: that one is about a lock arriving *after* a consent is live, this is about naming an already-dead account.

### F7 — A consumer-scoped grant API remains on the vendor trait with no callers and a comment inviting the trap · **LOW** · `CONFIRMED`

**Where:** [`Views.scala:39-46`](obp-api/src/main/scala/code/views/Views.scala#L39), [`MapperViews.scala:199-222`](obp-api/src/main/scala/code/views/MapperViews.scala#L199), [`MapperViews.scala:133-138`](obp-api/src/main/scala/code/views/MapperViews.scala#L133)

Commit `96e78387e` (#73) removed the only caller of `grantAccessToSystemViewForConsumer` / `grantAccessToCustomViewForConsumer` and explains at length why any caller would be a defect: `AccountAccess.consumer_id` holds the literal `ALL_CONSUMERS` rather than acting as a wildcard, and `revokeConsentAccountAccess` sweeps by exact equality on it, so a row written under a real consumer id is **structurally invisible to revocation, permanently**.

Both methods stayed on the trait — and so did the comments that recommend using them:

- `Views.scala:39-41`: *"Used by the consent flows: what one TPP's consent grants is that TPP's alone…"* — no consent flow uses them.
- `MapperViews.scala:133-138`: *"A grant that IS owned by one application — a consent exercised by a specific TPP — passes that TPP's consumerId instead"* — none does.

The same commit that documented the hazard left behind the two methods that trigger it, described as the recommended approach. Whoever reads the trait rather than the commit message gets the opposite advice.

**Suggested direction.** Delete both (nothing calls them, and the `Views` trait has one implementation in-tree). If they must stay for an out-of-tree implementation, replace the comments with the warning and make the invariant structural — have `revokeConsentAccountAccess` sweep every row for the shadow user regardless of `consumer_id`, which is safe because a shadow user is 1:1 with its consent and owns nothing else. Keep `revokeAccessToViewForUserAndConsumer` and `accessGrantedToUserForConsumer` — those are load-bearing.

### F13 — system views are marked firehose in the database, which the code never does · **MEDIUM** · `PLAUSIBLE` (provenance not established)

**Where:** [`MapperViews.scala:849-852`](obp-api/src/main/scala/code/views/MapperViews.scala#L849) (`unsavedSystemView`), [`APIUtil.scala:3611-3614`](obp-api/src/main/scala/code/api/util/APIUtil.scala#L3611) (`hasAccountFirehoseAccess`)

`unsavedSystemView` creates every system view with `isFirehose_(false)`, and `applyDefaultsForSystemView` sets it true for exactly one id, `SYSTEM_FIREHOSE_VIEW_ID`. That was also true one commit back (`311fba838^`), so no version in recent history creates the UK or Berlin Group views as firehose.

The local `obp-mapped` database has **16 system views with `isfirehose_ = true`**, including every UK and Berlin Group read view — `ReadAccountsBasic`, `ReadAccountsDetail`, `ReadBalances`, `ReadTransactionsBasic`, `ReadTransactionsDebits`, `ReadTransactionsDetail`, `ReadAccountsBerlinGroup`, `ReadBalancesBerlinGroup` — plus `accountant` and `auditor`.

`hasAccountFirehoseAccess` is consulted **before** the `AccountAccess` lookup and returns true when `view.isFirehose && canUseAccountFirehose(user)`. Locally `allow_account_firehose=true`, and 3 users hold `CanUseAccountFirehoseAtAnyBank` (24 hold the bank-scoped `CanUseAccountFirehose`). So on that instance those users read **every account** through views whose entire purpose is to be consent-scoped.

Two things this is *not*:

- **Not a consent bypass under the shadow-user model.** A UK consent's JWT carries `entitlements = Nil`, so its shadow user can never hold a firehose role — `resolveUKConsentPrincipal`'s scaladoc relies on exactly this. It matters for principals that *are* people holding the role.
- **Not introduced by PR #2881.** It is database state, and the same class as F2: a row that has drifted from what the code defines.

**Deliberately not folded into the F2 fix.** `ensureSystemViewUpToDate` reconciles the permission set only. Resetting `isFirehose_` too would *remove* access rather than narrow a field list, and the provenance of the `true` values could not be established — no code path in recent history writes them, so they came from an older version, a migration, or a manual edit. Switching off a firehose an operator may be relying on is not a change to make on an unestablished premise; it needs a deliberate decision and probably a survey of real deployments first.

The harness note this started from (`.local-testing/OBP-Hola/harness.py:36-39`) is accurate and worth heeding for any future probe work: a PSU holding a firehose role makes every consent-scope result meaningless, because the check short-circuits before consent is consulted.
